### Câu hỏi bổ sung

#### Biome 2.x — lint domains, coverage, và các plugin ESLint không có tương đương

**Domains tồn tại**: Biome 2.0 giới thiệu khái niệm "domain" — nhóm rule bật theo framework/ngữ cảnh phát hiện được từ dependency trong `package.json` (không cần cấu hình tay). Các domain đã xác nhận qua search: `next` (rule dành riêng cho Next.js — ví dụ `noHeadImportInDocument`), `react`, `test` (ngữ cảnh file test), `project` (rule cấp toàn dự án như import trùng lặp). Một domain `solid` cũng tồn tại (không liên quan tới cả 2 monorepo). **Coverage với `@next/eslint-plugin-next`**: KHÔNG đầy đủ — domain `next` của Biome chỉ map một phần rule (ví dụ `no-head-import-in-document`), tài liệu cộng đồng khuyến nghị rõ "nếu dự án phụ thuộc `@next/eslint-plugin-next`, GIỮ ESLint trong pipeline" vì Biome chưa có bộ tương đương đầy đủ.

**a11y group vs `eslint-plugin-jsx-a11y`**: Biome có domain/nhóm rule a11y riêng (built-in, không phải plugin tách rời như ESLint) nhưng coverage so với `jsx-a11y` chưa được xác nhận là 100% qua search này (chưa xác minh đầy đủ — cần đối chiếu trực tiếp bảng `biomejs.dev/linter/rules-sources/`).

**`organizeImports` assist**: Đây là action riêng (không phải "domain") tự sắp xếp import — đã dùng thực tế trong `bun run check` của medviet (`biome check .` gồm cả import sorting, xác nhận trong CLAUDE.md §6 "Biome: formatter + linter + import sorting").

**`noUnusedImports`**: Có sẵn trong Biome (rule lint chuẩn), coverage tương đương `eslint-plugin-unused-imports` mà target đang dùng (`eslint-plugin-unused-imports: 4.1.4`).

**React hooks rules**: Biome có `useExhaustiveDependencies` (tương đương `react-hooks/exhaustive-deps`) và `useHookAtTopLevel` (tương đương `react-hooks/rules-of-hooks`) — theo search, `eslint-plugin-react-hooks` có "full coverage" trong Biome.

**`useSortedClasses` (nursery) vs `prettier-plugin-tailwindcss`**: `useSortedClasses` nằm trong nhóm **nursery** (rule thực nghiệm, có thể đổi/xoá không báo trước) — cùng thuật toán sort với Tailwind CSS gốc, nhưng khác biệt quan trọng: (1) không đọc được `tailwind.config.js`/theme tuỳ biến như plugin Prettier (Biome dùng preset đơn giản hoá, custom utility phải khai tay trong config Biome); (2) Biome **gộp mọi whitespace/newline thành 1 dấu cách** khi sort, còn plugin Prettier giữ nguyên whitespace gốc. Vì đang **nursery** và target dùng Tailwind v4 (theme CSS-based, không còn `tailwind.config.js` truyền thống), rủi ro thực tế thấp hơn so với Tailwind v3 nhưng vẫn nên coi là thực nghiệm, chưa nên thay hẳn `prettier-plugin-tailwindcss` (target hiện không cài plugin này — chỉ Prettier core).

**Plugin không có tương đương trong Biome** (phải giữ ESLint riêng nếu cần đúng những rule này): `eslint-plugin-turbo` (rule `no-undeclared-env-vars` kiểm tra biến môi trường khai trong `turbo.json` — Biome không biết về cấu hình Turborepo); `eslint-plugin-react-compiler` (nay đã gộp vào `eslint-plugin-react-hooks`, nhưng dù vậy Biome cũng không có rule tương đương để phân tích compiler-safety của component/hook — đây vẫn là phân tích đặc thù React Compiler, ngoài phạm vi Biome). `@next/eslint-plugin-next` (đã nêu trên) cũng nằm trong nhóm này ở mức "chưa đầy đủ". [biomejs.dev/linter/rules-sources](https://biomejs.dev/linter/rules-sources/), [dev.to — Biome ESLint Prettier migration guide](https://dev.to/pockit_tools/biome-the-eslint-and-prettier-killer-complete-migration-guide-for-2026-27m)

#### TypeScript 7 (tsgo) — có phải bản Go port; `tsc --noEmit`/`paths`/Vite tsconfigPaths còn chạy không; xung đột Biome/Vitest/Storybook

Xác nhận: `typescript@7` trên npm **chính là** bản port native viết bằng Go (biệt danh "tsgo" hồi còn ở preview `@typescript/native-preview`), nay đã hợp nhất vào package `typescript` chính thức, binary vẫn tên `tsc`. **`tsc --noEmit` vẫn chạy được** (đây là lệnh cốt lõi của compiler, không đổi). **`paths` trong tsconfig vẫn hoạt động** — đây là field JSON được đọc trực tiếp, không đi qua phần Compiler API còn thiếu ổn định. **Vite `resolve.tsconfigPaths`** cũng an toàn vì nó tự đọc/parse file `tsconfig.json` (JSON thuần), **không** gọi qua TypeScript Compiler API (`ts.createProgram` và tương tự) — đây chính xác là phần TS 7.0 CHƯA ổn định (phải chờ TS 7.1) và là nơi gói tương thích `@typescript/typescript6` tồn tại để cứu các tool cần API cũ.

**Xung đột đã ghi nhận qua search**: `@storybook/addon-vitest` có lỗi khi chạy trên tooling dùng tsgo — `"process is not defined"`, `"isatty is not a function"`, lỗi đọc property của `undefined` — nguyên nhân sâu xa là các tool gọi `ts.createProgram()` (Corsa API của tsgo) sẽ nhận `TypeError` vì API đó "chưa tồn tại hoặc hành xử khác bản cũ". **Biome**: decorator có metadata (kiểu NestJS dùng), enum có runtime value, namespace phát sinh code — cả 3 vẫn cần `tsc` cổ điển compile, "strip mode" của TS 7 CHƯA thay được bước build này. Vì medviet (ref) đã tự vận hành `typescript@^7.0.2` + Vitest + Biome + có `@medviet/storybook` (không rõ có bật `addon-vitest` hay không — cần kiểm tra trực tiếp `apps/storybook/package.json` của medviet để biết chắc, ngoài phạm vi search này), nên rủi ro trên **có khả năng đã né được** bằng cách không dùng `addon-vitest` (test story qua Vitest độc lập, không qua Storybook test addon) — nhưng đây là suy luận cần xác minh, không phải xác nhận trực tiếp. #### Bun — packageManager field, catalog/catalogs, overrides, frozen-lockfile, bun.lock; Turbo + Bun

- **`packageManager` field**: medviet ghim `"packageManager": "bun@1.3.14"` ở root `package.json` — đây là field chuẩn npm/corepack, Bun đọc để tự-pin version khi ai đó chạy qua corepack.
- **`workspaces.catalog` / `catalogs`**: hỗ trợ từ khoảng **Bun 1.2+** (medviet ghim `engines.bun: ">=1.2.0"` — đúng khớp ngưỡng), và **Bun 1.3** đã ổn định thêm tính năng catalog trong khuôn khổ parity với pnpm (có ghi nhận 2 bug nghiêm trọng "Bun 1.3 Isolated Installs + Catalog Unusable" đã được vá ở các bản 1.3.x sau — nên chốt tối thiểu **Bun 1.3.14+ hoặc 1.4.0** thay vì chỉ dựa vào ngưỡng tài liệu 1.2, để tránh 2 bug đã biết). Cú pháp giống hệt pnpm: `catalog: {...}` (mặc định) + `catalogs: { <name>: {...} }` (đặt tên), package tham chiếu qua `"pkg": "catalog:"` hoặc `"catalog:<name>"`.
- **Đáng chú ý nhất cho việc migrate target sang Bun**: Bun có cơ chế **tự động migrate `pnpm-workspace.yaml`** — khi phát hiện file này, Bun đọc `packages` (workspace glob) và `catalog`/`catalogs` rồi **tự chuyển vào `workspaces` field trong root `package.json`** theo đúng format Bun cần. Vì target đang định nghĩa toàn bộ catalog trong `pnpm-workspace.yaml` (giống hệt cấu trúc đã đọc ở đầu file này), đây gần như là đường migrate "gõ 1 lệnh" (`bun install` trên thư mục có sẵn `pnpm-workspace.yaml`) thay vì phải chép tay từng catalog entry sang `package.json`.
- **`overrides`**: Bun hỗ trợ field `overrides` (giống npm) — medviet dùng nó để ghim `@types/react: 19.2.17` xuyên toàn repo (giải quyết version-skew mismatch), cú pháp thẳng, không cần plugin gì thêm.
- **`bun install --frozen-lockfile`**: hoạt động tương tự pnpm/npm — cài đúng theo `bun.lock`, fail nếu lockfile lệch với `package.json`; không ghi nhận breaking change nào ở Bun 1.4 cho hành vi này qua search.
- **`bun.lock`**: định dạng **text-based** (JSONC, đọc được, diff được trong PR) thay cho `bun.lockb` nhị phân cũ từ Bun 1.2 trở đi — mỗi entry cataloged dependency được resolve và ghi kèm trong lockfile để đảm bảo cài đặt nhất quán across máy. Bun 1.4 thêm integrity hash SHA-512 cho dependency kiểu GitHub/tarball.
- **Turbo 2 + Bun**: Turborepo 2.x tự phát hiện Bun qua `packageManager` field / `bun.lock` presence — không cần cấu hình thêm, đúng như cách medviet đang chạy `turbo run <task>` trên nền Bun workspaces.
- **`turbo prune` + Bun**: chưa xác minh trực tiếp qua search trong phiên này — theo hiểu biết chung `turbo prune` hỗ trợ cả 4 package manager chính (npm/yarn/pnpm/bun) từ Turbo 2.x, nhưng cần test thực tế trên Bun trước khi dựa vào cho Docker build (điểm này cần điều tra thêm, không nên coi là đã xác minh).
[bun.com/docs/pm/catalogs](https://bun.com/docs/pm/catalogs), [bun.sh/docs/pm/catalogs](https://bun.sh/docs/pm/catalogs), [bun.com/blog/bun-v1.3](https://bun.com/blog/bun-v1.3), [github.com/oven-sh/bun/issues/23615](https://github.com/oven-sh/bun/issues/23615)

### Điểm cần quyết định

Những chỗ bảng version ở trên không tự quyết được thay — cần user chốt trước khi thực thi:

1. **Radix UI → Base UI (`packages/ui` viết lại gần như từ đầu)**. Đây là quyết định nặng nhất trong toàn bộ báo cáo, không phải "bump version": target hiện có ~26 package `@radix-ui/react-*` riêng lẻ trong cả `packages/ui` lẫn `packages/ui-public`; medviet dùng **1 package** `@base-ui/react` + shadcn style `base-vega` + composition qua `render` prop (không phải `asChild`) + data-attribute dạng boolean trần (`data-open` thay vì `data-[state=open]`). Không có đường "bump" từ Radix sang Base UI — phải chạy lại `shadcn add` cho từng primitive theo style mới và sửa tay mọi chỗ dùng `asChild`. Cần quyết: giữ Radix (bỏ qua phần này của "mirror medviet") hay migrate hẳn sang Base UI.

2. **TypeScript 7 (tsgo) — chấp nhận rủi ro tooling ở mức nào**. `tsc --noEmit` + `paths` + Vite `resolve.tsconfigPaths` chạy tốt (đã xác minh qua tài liệu chính thức), nhưng: (a) Compiler API ổn định chưa có tới bản 7.1 — bất kỳ tool nào gọi `ts.createProgram`/`ts.transpileModule` trực tiếp có nguy cơ vỡ (cần audit `toolings/eslint`, các script build tuỳ biến); (b) `@storybook/addon-vitest` có ghi nhận lỗi khi chạy trên toolchain tsgo. Vì medviet (ref) đã chạy TS 7 trong production, rủi ro có vẻ đã được kiểm chứng thực tế bên đó — nhưng nên hỏi trực tiếp xem `apps/storybook` của medviet có bật `addon-vitest` không, và có gặp vấn đề gì cần workaround không, trước khi target đi theo.

3. **Vitest: lên đúng bản `4.1.10` (khớp ref catalog của medviet) hay lên thẳng `5.0.0` (npm latest tuyệt đối)?** Bản thân medviet CHƯA lên Vitest 5 — nếu mục tiêu là "mirror medviet" thì target nên dừng ở 4.x; nếu mục tiêu là "latest tuyệt đối" như user yêu cầu ban đầu thì phải chấp nhận đi trước cả repo tham chiếu (rủi ro cao hơn, ít được kiểm chứng thực tế trong hệ sinh thái medviet).

4. **React Router: SPA (7.18.3) hay framework-mode SSR (8.3.1)?** Target hiện chỉ có 1 app (`documents`) dùng `react-router` ở dạng SPA thuần (Vite, không SSR) — khớp với model `_template_vite` của medviet. Nếu không có nhu cầu SEO/SSR cho app đó, mục tiêu hợp lý là **7.18.3** (không phải 8.x) — bump lên 8 chỉ hợp lý nếu quyết định thêm 1 app kiểu `_template_reactrouter` (framework-mode, cần Node runtime riêng, không phải nginx tĩnh).

5. **Next.js 16 — mô hình cache mới (`cacheComponents`) có bật ngay không?** Đây không phải chỉ đổi tên: bật `cacheComponents: true` (thay `experimental.dynamicIO`/`experimental.useCache`/PPR cũ) có thể **lộ lỗi build** cho bất kỳ data fetch nào nằm ngoài `<Suspense>` — cần đọc riêng "Migrating to Cache Components" và quyết định có bật ngay lúc nâng cấp hay để sau (an toàn hơn: nâng Next 16 trước, giữ hành vi cache cũ, bật `cacheComponents` như một đợt riêng).

6. **`middleware.ts` → `proxy.ts`: có app nào trong target cần Edge runtime không?** `proxy.ts` của Next 16 CHỈ chạy Node.js runtime (không cấu hình được Edge). Nếu bất kỳ app nào (`mcp`, `assistant-ai`, `portfolio`, `_template`, `documents` không áp dụng vì không phải Next) cần Edge middleware thực sự (ví dụ để chạy ở CDN edge, latency thấp), phải **giữ `middleware.ts` cũ** thay vì đổi sang `proxy.ts` — cần rà từng app xem có dùng Edge runtime cho middleware không trước khi chạy codemod.

7. **`ai` SDK: 5→7 (bỏ qua major 6) có thực sự an toàn không?** Bảng đã xác nhận `@assistant-ui/react-ai-sdk@1.4.0+` mở peer range cho cả v6 và v7, nhưng **`@ai-sdk/google`** (provider hiện dùng, `^2.0.42`) chưa được kiểm tra version tương ứng — đây là gói NGOÀI danh sách được giao nghiên cứu nhưng LÀ phụ thuộc trực tiếp của app `assistant-ai`. Cần điều tra riêng version `@ai-sdk/google` tương thích `ai@7` trước khi thực thi, nếu không app AI có thể vỡ ở runtime dù mọi thứ typecheck qua.

8. **Giữ hay bỏ `@changesets/cli`?** Medviet (ref) **không dùng changesets** — mọi package trong `packages/*` của medviet là `private: true`, không publish npm, versioning không cần thiết. Target hiện dùng changesets cho `packages/hook-public` và `packages/ui-public` (2 package publish thật ra ngoài, `@fe-monorepo/*`). Nếu mirror kiến trúc medviet nghiêm ngặt (bỏ khái niệm "public package" luôn) thì changesets có thể bỏ hẳn thay vì bump lên v3; nếu vẫn cần publish 2 package đó ra ngoài thì phải bump và đọc kỹ migration guide v2→v3 riêng.

9. **Package manager: pnpm → Bun có nằm trong phạm vi "rebuild to mirror medviet" không?** Toàn bộ catalog/workspaces hiện tại của target viết bằng cú pháp `pnpm-workspace.yaml`. Bun có cơ chế tự động migrate file này khi phát hiện (xem mục Bun ở câu hỏi bổ sung) — nhưng đây vẫn là đổi package manager cho toàn monorepo (ảnh hưởng CI, Docker, lockfile, script `pnpm dlx`→`bunx`/`bun x`), không chỉ là "bump version" của 1 package. Cần chốt: có đổi sang Bun luôn (đúng 100% với medviet) hay giữ pnpm và chỉ mirror cấu trúc/pattern code.

10. **ESLint 9 + Prettier 3 → Biome 2.x?** Biome chưa có coverage đầy đủ cho `@next/eslint-plugin-next` và `eslint-plugin-turbo` (xem câu hỏi bổ sung) — nếu target vẫn có nhiều app Next.js (khác với medviet, vốn không có app Next.js nào), việc bỏ hẳn ESLint có thể mất một số rule an toàn/best-practice đặc thù Next.js và Turborepo. Cân nhắc mô hình lai (Biome cho format + phần lint chung, giữ ESLint riêng cho các rule Next-specific) thay vì thay thế 100% ngay từ đầu.

11. **Storybook: đi thẳng 8→10 (bỏ qua 9) hay dừng ở 9 làm bước đệm?** Hai lớp breaking (essentials addon bị xoá + ESM-only) cộng dồn nếu nhảy thẳng. ### 2.a — Bun workspaces

- `workspaces` là object (không phải mảng path như npm/yarn cổ điển) với 3 field: `packages` (mảng glob, vd `["apps/*","packages/*","tooling/*"]`), `catalog` (map version dùng chung — reference gọi là "root catalog"), `catalogs` (map các **named catalog** như `react19`, `tailwind4`, `tanstack-query5`, `react-router8`, `tanstack-table9`, `testing`) — tất cả khai báo thẳng trong root `package.json`, không có file `pnpm-workspace.yaml` tương đương (nguồn: https://github.com/oven-sh/bun/blob/main/docs/pm/cli/install.mdx; ref: `package.json` § `workspaces`).

- Package tham chiếu catalog bằng `"catalog:"` (root catalog) hoặc `"catalog:<name>"` (named catalog) trong `dependencies`/`devDependencies` — reference repo dùng cả hai dạng (vd `"typescript": "catalog:"`, `"@types/react": "catalog:react19"`) (nguồn: https://bun.com/docs/pm/catalogs; ref: nhiều `package.json` trong `packages/*`, `apps/*`).
- Thêm/nâng version catalog: sửa `catalog`/`catalogs` trong root `package.json` rồi `bun install`, hoặc dùng CLI ghi thẳng: `bun add react --catalog` (root) / `bun add vitest --catalog=testing` (named) (nguồn: https://github.com/oven-sh/bun/blob/main/docs/pm/cli/add.mdx).
- `overrides` — reference dùng để ghim `@types/react` (`"overrides": {"@types/react": "19.2.17"}`) ở top-level `package.json`, tương đương `pnpm.overrides`/`resolutions` (nguồn: ref: `package.json`).
- `bunfig.toml` của reference chỉ set `[install] linker = "isolated"` — layout `node_modules` kiểu isolated giống pnpm (mỗi package chỉ thấy đúng dependency khai báo, không "phẳng" như hoisted mặc định của Bun) — cờ này cần khi muốn giữ đúng hành vi strict-dependency của pnpm cũ (nguồn: ref: `bunfig.toml`; https://github.com/oven-sh/bun/blob/main/docs/pm/isolated-installs.mdx).
- **Migrate từ pnpm sang Bun — `bun install` TỰ ĐỘNG đọc `pnpm-lock.yaml`**: khi chạy `bun install` trong project chưa có `bun.lock`, Bun tự convert `pnpm-lock.yaml` **lockfileVersion 7–9** thành `bun.lock`, giữ nguyên file gốc; đồng thời **tự di dời** `workspaces` (packages), `catalog`/`catalogs`, `overrides`, và patched dependencies từ `pnpm-workspace.yaml`/`.pnpmfile.cjs` **vào `package.json`** — đúng thứ user cần khi chuyển catalog cũ trong `pnpm-workspace.yaml` sang `workspaces.catalog` (nguồn: https://github.com/oven-sh/bun/blob/main/docs/pm/lockfile.mdx, https://github.com/oven-sh/bun/blob/main/docs/pm/cli/install.mdx). Không migrate npm `lockfileVersion 1` (in ra warning, resolve lại từ `package.json`) (nguồn: như trên).
- `bun install --frozen-lockfile`: cài đúng version trong `bun.lock`, fail nếu `package.json` lệch với lockfile — dùng trong CI/Dockerfile builder stage (khớp cách reference repo dùng trong Dockerfile) (nguồn: https://github.com/oven-sh/bun/blob/main/docs/pm/cli/install.mdx; ref: `apps/_template_vite/Dockerfile`).

- **Reference Dockerfile thực tế (`apps/_template_vite/Dockerfile`, `apps/health-checkup/Dockerfile`) là biến thể 4 stage tương tự nhưng dùng Turborepo `prune` thay vì tự tách prod/dev deps**: *base* (`oven/bun:${BUN_VERSION}-alpine` + `apk add libc6-compat`) → *pruner* (`bunx turbo prune ${PROJECT} --docker`, sinh `out/json`, `out/full`, `out/bun.lock`) → *builder* (copy `out/json` trước để cache `bun install --frozen-lockfile`, rồi copy `out/full`, ghi `.env.${BUILD_ENV}` vào `.env`, chạy `bun -e "import '...env.ts'"` để **fail build sớm** nếu thiếu biến `PUBLIC_*`, cuối cùng `bun run build --filter=${PROJECT}`) → *runner* (`nginx:stable-alpine`, copy `dist` + `nginx.conf` riêng của app) (nguồn: ref: `apps/_template_vite/Dockerfile`, `apps/health-checkup/Dockerfile`).

FROM oven/bun:${BUN_VERSION}-alpine AS builder

COPY package.json bun.lock ./

COPY . .

FROM node:24-alpine AS runner

COPY --from=builder --chown=node:node /app/.next/standalone ./
COPY --from=builder --chown=node:node /app/.next/static ./.next/static

### 2.g — Env: `@medviet/env` (reference) và tương đương phía Next.js

- **API `@medviet/env` (reference)** rất nhỏ, 2 file: `createEnv` (`packages/env/src/create-env.ts` — chưa xác nhận tên file chính xác vì chỉ đọc được nội dung qua glob `packages/env/src/*.ts`) nhận `(schema: ZodType, runtimeEnv: unknown)`, chạy `schema.safeParse(runtimeEnv)`, throw `Error` kèm `z.prettifyError(parsed.error)` nếu invalid, trả `parsed.data` (typed) nếu hợp lệ — **không đọc `import.meta.env`/`process.env` bên trong**, nhận `runtimeEnv` từ tham số để dùng được cả ngoài Vite (script Bun thường, test của chính package) (nguồn: ref: `packages/env/src/*.ts`).

- API `createEnv` của `@t3-oss/env-nextjs` khác cấu trúc reference: nhận 1 object với 3 khối tách biệt — `server: {...}` (biến chỉ server đọc được, truy cập ở client sẽ throw runtime error), `client: {...}` (biến **bắt buộc tiền tố `NEXT_PUBLIC_`**, CLI/build sẽ báo lỗi nếu thiếu tiền tố), `shared: {...}` (đọc được cả 2 phía, vd `NODE_ENV`) — validate bằng Zod y hệt, nhưng `runtimeEnv` phải map tay biến-tới-`process.env.<KEY>` (Next.js không tự inline `process.env` như Vite làm với `import.meta.env`, nên phải liệt kê thủ công) — từ Next.js ≥13.4.4 dùng `experimental__runtimeEnv` chỉ cần liệt kê biến **client** (biến server tự đọc `process.env` runtime, không bị bundler inline) (nguồn: https://context7.com/t3-oss/t3-env/llms.txt, https://github.com/t3-oss/t3-env/blob/main/docs/src/app/docs/nextjs/page.mdx).
- `@t3-oss/env-nextjs` còn có cơ chế **`extends: [preset1(), preset2()]`** để gộp thêm biến chuẩn của nền tảng deploy (`vercel()`, `neonVercel()`, `uploadthing()`, `upstashRedis()`, import từ `@t3-oss/env-nextjs/presets-zod`) — biến các preset này tự động có type, không cần khai lại trong `server`/`client` (nguồn: https://context7.com/t3-oss/t3-env/llms.txt).
- **Khác biệt kiến trúc cần lưu ý khi map reference → Next.js**: reference dùng 1 schema phẳng (`baseEnvSchema.extend({...})`, tất cả đều tiền tố `PUBLIC_*`, vì Vite bake **mọi** biến `import.meta.env.PUBLIC_*` vào bundle — không phân biệt server/client vì SPA/SSR template không có khái niệm "server-only var" theo nghĩa Next.js) — còn `@t3-oss/env-nextjs` **buộc** phải tách `server`/`client`/`shared` vì Next.js App Router thật sự chạy code ở cả server và client, và để lộ 1 biến secret vào bundle client là lỗi bảo mật thật (không chỉ quy ước). Khi dựng `env.ts` cho app Next.js, KHÔNG thể copy nguyên `baseEnvSchema` phẳng của reference — phải phân loại lại từng biến `PUBLIC_*` cũ vào khối `client` (đổi tiền tố `PUBLIC_` → `NEXT_PUBLIC_`) và biến bí mật (API key, DB URL) vào khối `server` (nguồn: suy luận trực tiếp từ khác biệt API `createEnv` hai bên — ref: `packages/env/src/*.ts` vs https://context7.com/t3-oss/t3-env/llms.txt).
- `@t3-oss/env-nextjs` build trên `@t3-oss/env-core` (bản framework-agnostic, dùng `clientPrefix` tuỳ chỉnh thay vì cứng `NEXT_PUBLIC_`) — nếu 1 app trong monorepo Next.js không dùng Next.js (vd 1 script Bun thuần) thì dùng `@t3-oss/env-core` với `clientPrefix: "PUBLIC_"` sẽ gần giống ngữ nghĩa `@medviet/env` hơn (nguồn: https://context7.com/t3-oss/t3-env/llms.txt).

- `languages.ts`: **registry ngôn ngữ** = 1 mảng hằng `export const languages = ["vi","en"] as const`, suy ra type `LanguageCode`, và `defaultLanguage: LanguageCode = "vi"` — thêm ngôn ngữ chỉ cần thêm code vào mảng này, compiler tự báo thiếu file JSON tương ứng ở nơi khác (nguồn: ref: `packages/i18n/src/languages.ts`).

- Đây là **wiring theo app**: mỗi app gọi `createI18n({cookieName: "..."})` đúng 1 lần ở `~/libs/i18n.ts` (không đọc được trong lần khảo sát này, suy từ comment trong `create-i18n.ts`: "Call it exactly once per app, from that app's `~/libs/i18n.ts`") — khác `@medviet/dayjs` (tự extend ở module scope, không cần hàm khởi tạo) vì i18n cần nhận config app-specific (tên cookie) còn dayjs thì không.
- `change-language.ts`, `locales/vi.json`, `locales/en.json` chưa đọc chi tiết nội dung trong phiên nghiên cứu này — chỉ xác nhận tồn tại qua `ls` (nguồn: ref: `packages/i18n/src/` — liệt kê thư mục).

#### `@medviet/dayjs` — API + shape `exports`

- `package.json` có **root entry** DUY NHẤT trong toàn bộ workspace (`"." : "./src/dayjs.ts"`) + subpath (`"./*": "./src/*.ts"`) — lý do: root chính là singleton dayjs đã cấu hình, mirror cách import `dayjs` gốc (nguồn: ref: `packages/dayjs/package.json`; `.agents/rules/quality-avoid-barrel-imports.md`).
- `dayjs.ts`: import `dayjs` gốc + 4 plugin (`customParseFormat`, `relativeTime`, `timezone`, `utc` — **thứ tự extend load-bearing**: `utc` trước `timezone` vì timezone build trên offset helper của utc) + side-effect import 2 locale (`dayjs/locale/en`, `dayjs/locale/vi`), gọi `dayjs.locale(defaultLocale)` rồi `export default dayjs` — tất cả chạy ở **module scope** (không phải trong hàm `createDayjs()`) để ESM đảm bảo mọi nơi import đều nhận bản đã extend, không có "cửa sổ" nào import được bản dayjs trần chưa extend (nguồn: ref: `packages/dayjs/src/dayjs.ts`).
- **Không set `tz.setDefault()`** — timestamp render theo giờ **thiết bị** đọc, không hard-code timezone Việt Nam; nơi cần cố định 1 timezone thì gọi `.tz("Asia/Ho_Chi_Minh")` tại call site (nguồn: ref: `packages/dayjs/src/dayjs.ts` — docstring trong file).
- `formats.ts`: 7 hằng số format (không phải 6) — `DATE_FORMAT="DD/MM/YYYY"`, `YEAR_FORMAT="YYYY"`, `TIME_FORMAT="HH:mm"`, `TIME_WITH_SECONDS_FORMAT="HH:mm:ss"`, `DATE_TIME_FORMAT="DD/MM/YYYY HH:mm"`, `FULL_DATE_FORMAT="dddd, DD/MM/YYYY"`, `FULL_DATE_TIME_FORMAT="dddd, DD/MM/YYYY HH:mm:ss"` — day-first vì hồ sơ lâm sàng tiếng Việt đọc ngày trước; API trao đổi ISO string nên dayjs tự parse/serialize không cần token format (nguồn: ref: `packages/dayjs/src/formats.ts`).
- `locales.ts`: `export const locales = ["vi","en"] as const`, type `DayjsLocale`, `defaultLocale: DayjsLocale = "vi"` — **mirror registry của `@medviet/i18n` bằng value, không import** (đúng nguyên tắc package nền tảng không phụ thuộc package khác cùng tầng); mỗi code ở đây bắt buộc có side-effect import `dayjs/locale/<code>` tương ứng trong `dayjs.ts`, thiếu thì `dayjs.locale(code)` sẽ **âm thầm no-op** (nguồn: ref: `packages/dayjs/src/locales.ts`).
- `set-locale.ts`: `setDayjsLocale(locale: string)` — tách phần ngôn ngữ trước dấu `-` (`locale.split("-")[0]`) rồi kiểm tra có trong `locales` không, có thì set, không thì fallback `defaultLocale` — nhận `string` thường (không phải `DayjsLocale`) vì nguồn input là event `languageChanged` của i18next (kiểu `string` bất kỳ); tách theo nửa đầu mã ngôn ngữ để `navigator.language` trả `"en-US"` vẫn khớp `"en"` trong registry thay vì bị coi là không hợp lệ (nguồn: ref: `packages/dayjs/src/set-locale.ts`).
- `@medviet/i18n/change-language.ts`: `changeLanguage(language: LanguageCode)` — wrapper mỏng quanh `i18next.changeLanguage()`, chỉ khác là **ép kiểu tham số về đúng `LanguageCode`** (registry) thay vì `string` bất kỳ mà `i18next.changeLanguage` gốc chấp nhận (nguồn: ref: `packages/i18n/src/change-language.ts`).
- Package **cố ý không import `@medviet/i18n`** — giữ registry locale bằng value riêng, để không có cạnh ngược trong đồ thị import; app là nơi DUY NHẤT biết cả 2 package, nên bridge (`i18n.on("languageChanged", setDayjsLocale)`) nằm ở `~/libs/dayjs.ts` của từng app (nguồn: ref: `packages/dayjs/src/dayjs.ts` — docstring nêu rõ lý do).

#### Next.js — 2 lối làm i18n (không quyết định thay, chỉ liệt kê + trích dẫn)

**Lối A — i18next/react-i18next kiểu SSR thủ công** (gần giống bản chất reference nhất — vẫn dùng i18next làm lõi):
- Bộ package: `i18next`, `react-i18next`, `i18next-browser-languagedetector` (client), `i18next-resources-to-backend` (server — load JSON bằng `import()` động, chạy được cả Edge runtime lẫn Node vì không dùng timer/URL tương đối), `accept-language` (parse header `Accept-Language` phía server) (nguồn: https://www.locize.com/blog/i18n-next-app-router — blog chính thức của locize, đối tác lõi i18next).
- Server Component đọc bản dịch qua helper tự viết kiểu `getT()`: đọc ngôn ngữ từ header tuỳ biến (`x-i18next-current-language`) middleware set sẵn, trả về `{t, i18n}` sau khi load namespace xong; Client Component dùng `useT()` (hook tự viết) đọc ngôn ngữ qua `useParams()` trong route `[lng]`, cần `"use client"` (nguồn: https://www.locize.com/blog/i18n-next-app-router).
- `ssrBackend` chỉ dùng được với backend không timer/không URL tương đối như `i18next-resources-to-backend` — KHÔNG dùng được HTTP backend hay `i18next-locize-backend` ở phía server (nguồn: kết quả search dẫn từ tài liệu i18next chính thức về `ssrBackend`).
- Middleware tự detect ngôn ngữ qua cookie/`Accept-Language`/URL path, loại bỏ việc truyền tay ngôn ngữ xuyên component tree — kiến trúc gần nhất với cách reference dùng `i18next-browser-languagedetector` (nguồn: https://www.locize.com/blog/i18n-next-app-router).

**Lối B — `next-intl`** (framework i18n chuyên biệt cho Next.js App Router, KHÔNG dùng i18next):
- Bản mới nhất hiện tại: **4.14.2** (nguồn: `npm view next-intl version`, 2026-09-03).
- Cài: `npm install next-intl`, cấu hình plugin trong `next.config.ts` (`createNextIntlPlugin()` bọc `nextConfig`), khai `i18n/request.ts` với `getRequestConfig(async () => ({locale, messages: (await import(...)).default}))` để Server Component đọc messages theo locale, bọc `<NextIntlClientProvider>` ở root layout để Client Component nhận được config (nguồn: https://github.com/amannn/next-intl/blob/main/docs/src/pages/docs/getting-started/app-router.mdx).
- Có `createMiddleware()` factory riêng — tự resolve locale từ `Accept-Language` header + cookie + URL prefix, ghi vào response header `x-next-intl-locale` để tầng dưới đọc lại — tương tự cơ chế middleware của Lối A nhưng đã đóng gói sẵn, không phải tự viết `getT`/`useT` (nguồn: https://github.com/amannn/next-intl/blob/main/packages/next-intl/src/middleware/middleware.tsx).
- Khác biệt lớn nhất với reference: `next-intl` dùng **ICU message syntax** + API hoàn toàn khác `react-i18next` (`useTranslations()` thay `useTranslation()`), nên **không thể tái dùng thẳng** `packages/i18n/src/locales/*.json` viết theo cấu trúc `react-i18next` (`{translation: {...}}` namespace phẳng) — cần chuyển đổi format message nếu chọn lối này.

### 2.i — Testing: Vitest config shape, Playwright config, Vitest 4 `projects`

#### Vitest — shape `apps/_template_vite/vitest.config.ts` (ref: đã đọc trực tiếp)

- Dùng `mergeConfig(viteConfig, defineConfig({test: {...}}))` từ `vite`/`vitest/config` — tái dùng nguyên `vite.config.ts` của app (React Compiler, alias `~/*`, …) thay vì khai lại resolver riêng cho test (nguồn: ref: `apps/_template_vite/vitest.config.ts`).
- **`TZ=UTC` pin bằng `process.env.TZ = "UTC"` VIẾT THẲNG ở đầu file config** (trước khi Vitest fork test worker, để worker kế thừa biến env này) + lặp lại trong `test.env: {TZ: "UTC"}` — comment trong file giải thích rõ: không dùng `TZ=UTC vitest` qua CLI vì cú pháp prefix-env đó **không hợp lệ trên PowerShell/cmd** (repo dev trên Windows) (nguồn: ref: `apps/_template_vite/vitest.config.ts`).
- `test.environment: "jsdom"`, `test.setupFiles: ["./vitest.setup.ts"]`, `test.globals: true`, `test.include: ["test/**/*.{test,spec}.{ts,tsx}"]` (chỉ quét cây `test/`, không quét `src/`) (nguồn: ref: `apps/_template_vite/vitest.config.ts`).
- `test.coverage`: `provider: "v8"`, `reporter: ["text","html"]`, `include: ["src/**/*.{ts,tsx}"]`, `exclude` loại `src/index.tsx`, `src/vite-env.d.ts`, mọi `.d.ts` (entrypoint/generated type không có hành vi để test) (nguồn: ref: `apps/_template_vite/vitest.config.ts`).
- `vitest.setup.ts`: import `@testing-library/jest-dom/vitest` (matcher DOM), `beforeAll` gọi `i18n.changeLanguage("vi")` (import trực tiếp `~/libs/i18n` — dùng đúng catalog dịch thật của app, không mock — để `t("...")` trong test resolve ra chuỗi người dùng đọc thật, đồng thời PIN cứng ngôn ngữ vì i18next mặc định sẽ detect `navigator.language` của jsdom, làm cùng 1 assertion ra kết quả khác nhau tuỳ máy), `afterEach` gọi `cleanup()` (RTL) + `vi.clearAllMocks()` (nguồn: ref: `apps/_template_vite/vitest.setup.ts`).

#### Playwright — shape `apps/_template_vite/playwright.config.ts` (ref: đã đọc trực tiếp)

- `testDir: "./e2e"`, `testMatch: "**/*.e2e.ts"` — bắt buộc khai `testMatch` thủ công vì glob mặc định của Playwright **không khớp** hậu tố `.e2e.ts` (khác `.spec.ts` mặc định) — hậu tố này cố ý để tách khỏi Vitest, Vitest chỉ quét `test/**/*.{test,spec}...` nên 2 runner không bao giờ đụng file của nhau dù cùng nằm ở root app (nguồn: ref: `apps/_template_vite/playwright.config.ts`).
- `expect.timeout: 5_000` (Playwright chờ lâu hơn 1 assertion jsdom), `fullyParallel: true`, `forbidOnly: !!process.env.CI` (1 `test.only` bị commit nhầm sẽ FAIL cứng trên CI thay vì âm thầm skip phần còn lại), `retries: CI?2:0`, `workers: CI?1:undefined`.
- `reporter`: local dùng `"list"`; CI dùng mảng `[["list"],["html",{open:"never"}],["junit",{outputFile:"junit.xml"}]]` — JUnit XML để widget test của MR đọc được, không chỉ nằm trong log job.
- `use.locale: "vi-VN"` — Chromium mặc định `en-US`, nếu không pin thì assertion trên text tiếng Việt sẽ **chỉ fail trên CI** (Chromium thật) chứ không fail ở component test (jsdom không detect theo cách này) — đối xứng với việc pin `vi` trong `vitest.setup.ts`.
- **2 project cùng chạy trên 1 bộ spec**: `chromium` (mặc định CI + `bun run e2e`, mỗi test 1 browser context mới — đúng cô lập Playwright chuẩn) và `watch` (chỉ dùng cho `e2e:headed`, bật `reuseContext: true` — giữ 1 cửa sổ browser suốt cả run thay vì mở mới mỗi test — kèm `launchOptions.slowMo: 500` + `timeout: 0` để chạy chậm-quan-sát-được; comment trong file cảnh báo `reuseContext` là **experimental**, việc reset state giữa các test là "best-effort", nên KHÔNG BAO GIỜ dùng project này cho CI) — luôn phải **đặt tên project tường minh** khi chạy lệnh, vì `playwright test` trần sẽ chạy CẢ HAI project cùng lúc (nguồn: ref: `apps/_template_vite/playwright.config.ts`).
- `webServer.command: "bun run build && bun run preview --port 3000 --strictPort"`, `reuseExistingServer: !process.env.CI`, `stdout: "pipe"` (mặc định Playwright bỏ qua stdout của webServer — nếu không set `pipe`, 1 lỗi build thật sẽ hiện ra là "timeout không rõ nguyên nhân" thay vì lỗi compiler thật), `timeout: 180_000` (build cold trên runner CI chậm hơn máy dev) — webServer build bản **production thật** để E2E test đúng bundle đã bake `PUBLIC_*` tại build time, không phải dev server có HMR/env khác (nguồn: ref: `apps/_template_vite/playwright.config.ts`).

#### Vitest 4 — `projects` (đổi tên từ `workspace`) cho 1 runner root-level

- **`test.workspace` đã bị GỠ HẲN ở Vitest 4** (không còn hỗ trợ file `vitest.workspace.*` nữa) — dùng field cấu hình này giờ ném lỗi cứng ngay khi resolve config: `"The test.workspace option was removed in Vitest 4. Please, migrate to test.projects instead."` (nguồn: https://github.com/vitest-dev/vitest/blob/main/packages/vitest/src/node/config/resolveConfig.ts).
- Thay thế: `test.projects` trong 1 `vitest.config.ts` **root-level duy nhất**, nhận mảng — mỗi phần tử có thể là (a) object config con inline (`{test: {name: "Unit"}}`), hoặc (b) **đường dẫn glob tới file config con của từng package** (vd `"./packages/app/vitest.config.ts"`) — cách (b) là cách áp dụng đúng cho monorepo kiểu reference: 1 root `vitest.config.ts` liệt kê glob tới `apps/*/vitest.config.ts` + `packages/*/vitest.config.ts` thay vì mỗi package tự chạy Vitest độc lập qua `turbo run test` (nguồn: https://github.com/vitest-dev/vitest/blob/main/docs/guide/projects.md, https://github.com/vitest-dev/vitest/blob/main/docs/guide/examples/projects-workspace.md).
- Lợi ích nêu trong changelog Vitest 3.2 (giai đoạn deprecate `workspace`, dọn đường cho Vitest 4 gỡ hẳn): gom cấu hình global (reporter, coverage) về 1 chỗ, và tránh xung đột tên `workspace` với field cùng tên của công cụ khác (ví dụ pnpm workspace) (nguồn: https://github.com/vitest-dev/vitest/blob/main/docs/blog/vitest-3-2.md).
- **Reference hiện KHÔNG dùng `projects`** — mỗi app/package tự có `vitest.config.ts` riêng, chạy độc lập qua Turborepo task `test` (`dependsOn: ["^topo","^build"]`) — đây là lựa chọn kiến trúc hợp lệ khác với `projects` (Turborepo lo song song hoá + cache theo package, Vitest `projects` lo gộp 1 tiến trình Vitest chạy hết); khi dựng repo mới cần quyết định 1 trong 2 mô hình, không trộn lẫn nửa vời (nguồn: ref: `turbo.json` § task `test`; suy luận kiến trúc, không phải trích dẫn docs).
